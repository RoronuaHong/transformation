# 视频 + 图片「画面内容可检索」落地方案

> 目标：对齐业界 DAM / Agentic DAM 最佳实践（§16.2 / §17.2 / §18.2 / Cloudinary·Canto·Aprimo），
> 让"视频/图片画面里出现的内容"（如实物「排骨」）也能被文本检索出来，而不依赖画面上的文字或文件名。
> 本文档是落地依据，实施严格按步骤推进，每步以 `eval_search.py --gate` 为回归闸门。

---

## 0. 对齐的最佳实践依据

| 来源 | 关键结论 | 本项目落点 |
|---|---|---|
| §16.2 三文件分离 Job4 | 多模态模型读 Proxy + 关键帧，生成画面描述/标签 + 向量写入库 | 本方案核心：抽帧 + VLM 打标 → sidecar |
| §17.2 / §17.4（验证报告 E 维度） | 视觉相似度搜索已落地；**以图搜图强、以文搜图弱（零样本 CLIP 对垂类内容）** | 文本搜画面不能只靠 CLIP → 主用 VLM 描述 |
| §18.2 能力2 | 多模态语义检索 = 文本搜视频 / 图搜视频 / 相似片段 | 双通道：VLM 描述（主）+ CLIP 文本→帧（补） |
| Cloudinary / Canto / Aprimo（Enrichment·Understanding） | 理解画面是 DAM 核心，不只靠标签/文字 | VLM 生成"画面描述 + 标签"文本 |

---

## 1. 总体架构（复用 OCR 同构）

完全镜像已验证、门禁零回归的 OCR 三通道架构（**关键：不另起炉灶**）：

- 新增派生 sidecar 目录 `index/visual/`，每素材 `index/visual/<id>.txt`（派生、可重建、**绝不写 DB `description`**）。
- 新增 `visual_runner.py`（镜像 `ocr_runner.py`）：子进程调**本地多模态 VLM**，对每帧输出「画面描述 + 标签」。
- 新增 `visual_material()`（镜像 `ocr_material()`）：ffmpeg 抽帧 → 调 runner → 落 sidecar；幂等、记 history、作用于 `VISUAL_KINDS=(videos, silent, images)`。

---

## 2. 两条检索通道

### 通道 A（主，对齐 §16.2）：VLM 生成的画面描述/标签
- 词法：`_score` 新增 `_VISUAL_FIELD_WEIGHT = 0.35` 独立通道（同 OCR 权重），命中稀有画面词（"排骨""红烧肉"）。
- 语义：`doc_text` 拼入 visual 文本 → 进 bge-m3 稠密检索（中文查询直接命中描述文本，绕开 CLIP 文本弱项）。
- 全文：`_material_text` 收录 visual sidecar，供长文档分块检索。
- 效果：查"排骨" → 命中画面里是排骨的素材，即使无任何文字。

### 通道 B（补）：CLIP 文本 → 帧
- 复用 `clip_runner` + `image_embeddings`，将素材扩展为**每帧一个 CLIP 向量**（现有只索引单图，需扩成多帧）。
- 查询文本用 CLIP text encoder 编码比对。文档已证**对垂类弱**，仅作补充通道，不当主依赖。

---

## 3. 落地步骤（文件/函数级）

1. `core.py`：加 `VISUAL_DIR`、`visual_sidecar_path()`（镜像 `ocr_sidecar_path`）、`_visual_text()`（带 (mtime,size) 缓存，镜像 `_ocr_text`）。
2. `core.py`：在 `_score` / `doc_text` / `_material_text` 三处各插入 visual 通道（权重 0.35，不碰主字段）。
3. `core.py`：加 `visual_material(mid, frames=N, force=)`，ffmpeg 抽帧逻辑复用 OCR 的（视频按关键帧/均匀采样，图片单帧）。
4. `visual_runner.py`：新文件，调本地 VLM 出「描述+标签」JSON（UTF-8 双保险，同 ocr_runner）。
5. `core.py auto_process_material`：链改为 `make_thumb → tech → describe → ocr → visual → shots → phash`，新素材入库即自动出画面描述。
6. `cli.py`：加 `visual <id>|--all [--apply]`（镜像 `ocr`）。
7. `mcp_server.py`：加 `run_visual` 工具（写 sidecar → 需 `confirm=true`，同 `run_ocr`）。
8. 帧采样策略：视频默认均匀抽 N 帧（同 OCR 的 frames=5），可选复用 `build_shot_index` 关键帧提升覆盖。
9. 通道 B：扩展 `image_embeddings` 支持多帧；新增文本→帧比对入口（CLI/MCP 可选）。

---

## 4. 必须守住的约束（铁律 + 门禁）

- **铁律（§23.3 / OCR 教训 / §24.3 三合一）**：visual 文本**只能走 sidecar + 独立低权重通道**，**绝不写 `description`**（主排序 1.5 权重）。否则门禁 ndcg 会 0.84→0.80 式退化。
- **门禁不退化**：任何改动先跑 `eval_search.py --mode lexical --gate`（基线 p5 .71 / r20 .78 / mrr .85 / ndcg .84，容差 .02）。新增**人工标注 GT 查询**（如"排骨"→ 画面有排骨的素材 id 集合）验证真能召回。
- **异步消化**：抽帧 + VLM 推理吃算力，必须进现有 `enqueue_autoproc` 后台异步链，不阻塞 API。

---

## 5. 头号前置：本地多模态 VLM 可用性（Step 0 先确认）

当前 ollama 已装：`bge-m3 / nomic-embed-text / gemma4:e2b / translategemma:4b / 两个 bge-reranker`。
**无一确认是多模态（看图）模型**（translategemma 是翻译、bge 是文本/重排）。

- Step 0 先验证 `gemma4:e2b` 是否支持图像输入。
- 若否，则 `ollama pull` 一个视觉模型（llama3.2-vision / gemma3:4b-it / qwen2.5-vl / minicpm-v）。
- 环境标称"全离线"，但 bge-m3 / reranker 是近期拉到 → 联网拉模型间歇可用；需确认网络/磁盘（视觉模型 2–8GB）。
- 若最终无视觉模型：通道 A 不可行，只能退守通道 B（CLIP 文本→帧），其对"排骨"类垂类不可靠，目标无法完全达成。

## 6. 验证计划

1. 选 2–3 条画面明确含某物体的素材（如烹饪视频）跑 `visual`，看 sidecar 描述质量。
2. 写 GT：`eval_ground_truth.json` 加窄查询（"排骨"等），人工核对相关 id。
3. `eval_search.py --mode lexical --gate` 必须 PASS；A/B 确认未稀释旧查询。
4. 端到端：Web 面板搜"排骨" → 出现画面里是排骨的素材（非靠文字）。

### 验证结果（2026-10-08）
- **通道 A**：`cli.py visual <id>` 端到端跑通（抽帧→gemma4:e2b→写 `index/visual/<id>.txt`）；"排骨"等画面词经标准 `search()` 即可命中，无需画面文字。
- **通道 B**：`build_clip_frame_embeddings` 建多帧向量成功；`imgsearch --text "排骨"` 返回跨帧召回（score ~0.28）。文档已载明 CLIP 文本→垂类弱，故通道 A 为主、B 为补充。
- **门禁零回归**：lexical gate 仍 PASS，且指标因新增 visual 文本反略升。
- **铁律守住**：visual 文本只进 sidecar + 0.35 低权重通道，**绝不写 `description`**（主排序 1.5）。

### 后续建议（未做）
- 为"画面内容"类查询补人工标注 GT（如"排骨"→ 画面有排骨的素材 id 集），固化进 `eval_ground_truth.json`，使门禁可量化验证画面召回。
- 批量跑 `visual --all`（需 ollama 在线；建议先 `--limit` 小批验证 VLM 描述质量）。
- `auto` 全链现已含 visual，批处理会触发 VLM 推理（重算力）；ollama 离线时自动 skipped，不影响其它步骤。
