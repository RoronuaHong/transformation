# 影视素材中心系统（Materials Hub）+ Agent：最佳实践分析与优化路线

> 目的：以数字资产管理（DAM）、混合检索 / RAG、Agent / MCP 工具设计、本地 AI 系统工程四套成熟最佳实践为镜，
> 对当前「影视素材中心 + subtitle_pipeline 联动 + MCP Agent 接口」做一次体系化体检，
> 给出「当前已做到 / 部分做到 / 缺失」的对照，以及可落地的优化路线（P0/P1/P2）。
> 本文档不重写代码，只做评估与规划；具体改动见末节路线。

## 0. 当前系统速写（评估基线）

| 项 | 现状 |
|---|---|
| 定位 | 单机个人级 DAM，零依赖（纯标准库 + 单页前端），全离线 |
| 数据规模 | 344 条 / ~3.3GB；341 条为 subtitle_pipeline 外部引用（原路径引用，不复制） |
| 存储 | SQLite 索引 `index/hub.db`（派生，可重建）+ 磁盘原文件（唯一真相源） |

| 联动 | `bridge_subtitle.py` 只读扫描 SP 4 个 scope，自动归类 + 受控标签 + 登记；支持轮询守护 `--watch` |

主要差距集中在**安全（无鉴权）、评估自动化、中文语义深度、Agent 写操作护栏、以及事件驱动联动**五处。

## 1. 分析框架（最佳实践清单）

把四类实践拆成可打分的维度：

| 维度 | 关键最佳实践 |
|---|---|
| **A 元数据与分类法** | 受控词表（controlled vocabulary）；维度化 `key:value` 分面；自由文本与标签分离；可扩展枚举 |
| **B 存储与索引** | 索引可派生/可重建（文件为唯一真相）；checksum 去重与完整性；外部引用可追溯；版本/溯源 |
| **C 检索 / RAG** | 混合检索（BM25 + 稠密 + rerank）；查询扩展/同义词；RRF 融合；文档分块 + 元数据过滤；离线评估（P@k / R@k）与回归门禁 |
| **D 引用完整性** | 失效巡检、感知、安全清理（只删索引）、可恢复 |
| **E Agent / MCP** | 工具窄而专一、结构化返回、只读优先、破坏性操作需确认；MCP 能力与错误处理规范；防 token 膨胀（分页/摘要） |
| **F 离线优先 / 隐私** | 本地推理、数据不出机、无外部依赖 |
| **G 可观测 / 评估 / 运维** | 结构化日志、健康端点、评估套件、一键重建 |
| **H 安全** | 鉴权/鉴权边界、输入校验（防路径穿越）、CORS/网络暴露控制、最小权限 |

## 2. A 维度：元数据与分类法 —— 评分：✅ 优秀

**最佳实践对照**
- ✅ **受控词表**：`sp | <platform> | job:<id> | type:<...> | lang:<xx>` 维度化标签，README 明确「请勿自由发挥」并规定扩展规则（只扩 `type:` 枚举、新平台加白名单、统一小写）。这正中 DAM 核心——先定分类法，检索/分面才靠谱。
- ✅ **维度化分面**：`key:value` 形式天然支持分面过滤（面板可按 `type:`/`job:`/`lang:` 组合筛），符合「关键词 + 多维度同时过滤」的成熟范式。
- ✅ **自由文本与标签分离**：要求把非结构化描述放 `description`，不放 tags。
- ⚠️ **部分**：标签体系完全由人工/bridge 手工打，**缺少自动标签生成**（见 P1）；`description` 多数来自 `fetch_meta.json` 的 title，稀疏。

**优化点**：建立「标签治理」——定期用 `core.distinct_tags()` 审计僵尸标签；自动打标补 `description` 与衍生标签。

## 3. B 维度：存储与索引架构 —— 评分：✅ 优秀（缺版本/溯源）

**最佳实践对照**
- ✅ **索引可派生、可重建**：`hub.db` / `thumbs/` / `embeddings` 全部声明为派生数据，删除即重建；「文件是唯一真相源」原则写进 README 运维章节——这是本地库长期稳定运维的关键，也是很多自建 DAM 没做对的。
- ✅ **checksum 去重**：SHA-256 收口去重（`duplicates()` / `kind` 重复组），历史可查。
- ✅ **外部引用零复制**：`location='external'` + `external_path`，省盘、幂等、不动原工程；预览按需 `Range` 读原文件。
- ⚠️ **缺失**：**版本管理与溯源（provenance）**——素材更新覆盖索引、不上历史；无法回答「这份素材料理记录 / 谁在何时改的标签」。对影视流水线（重跑 batch 覆盖目录）尤其有用。
- ⚠️ **缺失**：外部引用的 **path 合法性校验**（见 H 维度安全项）。

**优化点**：在 `embeddings`/`materials` 之外加一张轻量 `history` 表记录标签/描述变更；bridge 登记时校验 `external_path` 落在已知 SP 根目录内。

## 4. C 维度：检索 / RAG —— 评分：✅ 优秀（中文深度不足）

**最佳实践对照**
- ✅ **混合检索落地**：词法（字段加权 + 同义词 + 松匹配）⊕ 稠密（本地 embedding）+ **RRF 融合**，且「语义只补召回、不埋精确命中」的设计取舍正确——这正是 RAG 工业界反复验证的结论。
- ✅ **查询扩展/同义词表**：把中文意图映射到语料英文词，实测把中文 P@5 从 0.00 拉到 0.44。这是「无多语模型时中文检索」的务实解法。
- ✅ **去均值居中**：稠密相似度「减语料均值再算余弦」，规避句向量各向异性（本库两两余弦均值 0.76 的实测），说明团队做过严谨实验而非套公式。
- ✅ **增量索引 + 文档指纹**：向量带指纹，文本没变就跳过，避免全量重建。
- ⚠️ **中文语义依赖英文单语模型**：`nomic-embed-text` 是英文模型，中文真正起作用的是同义词层；换 `bge-m3` 等多语模型可显著改善（已在 README 已知限制中诚实标注）。
- ⚠️ **缺 reranker**：当前 RRF 后无交叉编码器重排，对中长查询的 top 精度有上限。
- ⚠️ **缺文档分块**：`description`/notes md 整段当 doc_text，对长笔记的命中粒度粗；应按段落/标题分块并带 chunk 级元数据。
- ⚠️ **缺离线评估门禁**：P@5 数字写进了 README，但没有**可重复跑的评估脚本 + ground truth 固化**，回归不可防。

**优化点**：① 评估套件化（固化 9 查询 ground truth，CI/手动一键算 P@5，设回归阈值）；② 引入 `bge-m3`/reranker 做 A/B；③ 长文档分块检索。

## 5. D 维度：引用完整性 —— 评分：✅ 优秀

数据层 / 接口层 / 界面层 / 卡片层 / CLI 层五层全覆盖，且贯彻「**只删索引、绝不碰磁盘**」的安全铁律，并能在原文件恢复后幂等重登记。这是外部引用模式最容易翻车的地方，项目处理得干净。无显著优化点，仅建议把巡检做成**定时任务 + 主动告警**（见 P1）。

## 6. E 维度：Agent / MCP 接口 —— 评分：⚠️ 基本可用，护栏不足

**最佳实践对照**
- ✅ **工具窄而专一**：4 个工具职责清晰（检索/取单条/标签/健康），非巨型「do_everything」工具。
- ✅ **结构化返回 + 防 token 膨胀**：`_brief()` 只回精简字段，大字段（全文档、大 base64）不进协议——这是 Agent 工具设计的要点（避免把整段素材塞进上下文）。
- ⚠️ **缺只读护栏**：工具当前对 Agent 是**只读**（好），但未在 schema 上声明只读属性；若将来加 `register_asset`/`tag` 写工具，必须显式「破坏性操作需 `confirm=true` 参数 + 二次确认」，否则 Agent 自主调用会误改库。
- ⚠️ **MCP 能力未协商**：`initialize` 直接回固定 `capabilities`，未根据运行环境动态声明（如 embedding 不可用时应关掉语义相关 hint）。
- ⚠️ **缺资源(Resources)**：把「最近登记素材」「某 job 全套」做成 MCP Resource，Agent 可像读文件一样订阅，比反复调工具更省 token。
- ⚠️ **缺流式/分页协议**：`search_materials` 一次回 N 条，海量结果下应考虑 cursor 分页。

**优化点**：① 写操作工具加 `confirm` 护栏；② 按 embedding 可用性动态声明 capabilities；③ 增 `read_text_preview`/`register_asset` 工具与 `recent://` 资源；④ 文档化「Agent 工作流示例」（如「找出所有缺封面的基准视频并批量生成」用现有工具编排）。

## 7. F 维度：离线优先 / 隐私 —— 评分：✅ 标杆

零依赖、全离线、数据不出机、可丢容器里跑——是本项目最突出的工程气质，也契合「本地影视素材含未公开内容」的隐私诉求。保持，并在对外暴露（见 H）时仍以「不出网」为前提。

## 8. G 维度：可观测 / 评估 / 运维 —— 评分：⚠️ 中上

- ✅ `/api/health` 健康快照、`/api/stats` 进度、bridge_state.json、派生数据一键重建、ollama 自动拉起——运维友好。
- ⚠️ **无结构化日志**：server/MCP 只有零星星 stderr，`stderr` 未带请求 id/耗时，排障靠猜。
- ⚠️ **无评估门禁**：见 C 维度。
- ⚠️ **无指标埋点**：检索延迟、命中率、失败率未量化。

## 9. H 维度：安全 —— 评分：❌ 最大短板

- ❌ **无鉴权**：服务监听 `0.0.0.0:8000`、MCP 进程可被本机任意进程调用；局域网内任何人可读/写/删。**当前仅适合本机或可信局域网**。这是上线前必须补的。*（→ 2026-09-27 已落地 P0-2 token 鉴权 + 默认 `127.0.0.1`，见 §14）*
- ⚠️ **路径校验缺失**：`/api/file/<id>` 读 `external_path`，若 `external_path` 未限制在项目根内，存在**任意文件读取（路径穿越）**风险（虽 external_path 来自 bridge 扫描而非用户输入，但 DB 若被写坏即失控）。
- ⚠️ **CORS/曝露面**：未显式设 CORS，默认同源尚可；一旦要跨机访问需收敛。

**优化点（P0）**：① 加简单 token 鉴权（server + MCP 共享一个 `VITUAL_HUB_TOKEN`）；② `ingest_external`/`bridge` 时校验 `external_path` 在已知根目录内，拒绝越界；③ 把监听改为默认 `127.0.0.1`，对外才绑 `0.0.0.0` 并配 token。*（→ ①②③ 均已于 2026-09-27 落地，见 §14 P0-1/P0-2）*

## 11. 优化路线（按优先级）

### P0 — 上线前必补（安全 + 防退化）
1. **鉴权（token）**：server 与 MCP 共享 `VITUAL_HUB_TOKEN`；MCP server 启动校验环境变量，调用方（CodeBuddy）在 `mcp.json` 传 `--token`。默认监听 `127.0.0.1`，仅跨机时绑 `0.0.0.0` 且强制 token。
2. **路径校验**：`ingest_external` / bridge 登记时，断言 `external_path` 落在已知根（`subtitle_pipeline/`、`materials_hub/materials/` 等）内，越界拒绝；`/api/file` 读取前再校验一次，杜绝路径穿越。
3. **评估门禁固化**：把 README 里 9 个中文查询 + ground truth 固化成 `eval_search.py`，一键输出 P@5/R@20 并打印与基线 diff；任何检索改动先跑它，防回归（这是把「已做到的 0.71」锁住的关键）。

### P1 — 体验与质量跃迁
4. **中文语义升级**：接入多语模型 `bge-m3`（ollama 本地）替换/并行 `nomic-embed-text`，并重测 P@5；可选加 `bge-reranker-v2` 做 RRF 后交叉重排（top 精度上限再抬）。
5. **自动打标**：注册 ollama 的 LLM（如 qwen2.5）在 bridge / upload 时，对 `description` 为空或 `type:media` 的素材生成描述 + 衍生标签（题材/场景/画质），写回 `description`/`tags`。**让「素材中心 + Agent」从「被动编目」变「主动理解」**——这正是 Agent 最需要的元数据肥度。
6. **事件驱动联动**：在 subtitle_pipeline 收尾（`discover/run_batch.py` 或 `vitual_mcp`）调用素材中心 `POST /api/register`（新增接收绝对路径的注册接口），替换 `--watch` 轮询；延迟更低、不常驻进程。
7. **审计与告警**：`bridge --prune` 定时化（任务计划）+ 失效超阈值时写 `/api/health` 的 `alerts` 字段，便于监控轮询告警。

### P2 — 规模与成熟度
8. **长文档分块检索**：notes/md/json 按段落分块 + chunk 级元数据，命中粒度从「整段」细到「段落」，配合 FTS5 替代手写词法打分（10 万级规模更稳）。
9. **向量索引**：`sqlite-vec` / HNSW 替代暴力扫描，规模上量后检索延迟不退化。
10. **版本与溯源**：`history` 表记录标签/描述/外链变更；支持「回看某素材上次怎么标的」。
11. **转码代理 / 多库隔离 / MCP Resource**：低码率预览版、按项目分库、`recent://` `job://` 资源订阅。

## 12. 针对「Agent」的专项建议

把素材中心视为 Agent 的**长期外部记忆（RAG corpus） + 工具集**，最佳形态：

- **读多写少，写必确认**：Agent 默认只用 4 个只读工具；任何 `tag`/`remove`/`register` 必须经 `confirm=true` 且最好有人类复核环节（Human-in-the-loop）。
- **把评估当 Agent 质量门禁**：每次改检索/打标，跑 `eval_search.py`，P@5 掉 0.05 即阻断——Agent 检索质量可量化、可回归。
- **最小化进上下文**：`_brief()` 已做字段裁剪，新工具继续遵守「只回 id/name/kind/tags/thumb，绝不回大字段」；万级结果用 cursor 分页而不是一次塞满。
- **编排高层工作流**：在 CodeBuddy 里把现有工具组合成 Agent 技能，例如
  `「找 type:benchmark 里还没封面的视频，批量生成」` = `list_tags` → `search_materials(type:benchmark)` →
  过滤 `thumb==false` → `POST /api/thumbs {ids}`。这类「素材中心 Agent 技能」是 P1 的高价值产物。
- **隐私边界**：Agent 全程本地调用，素材内容不出机；若接云端 LLM 做自动打标，仅传 `description`（元数据），不传原始视频帧。

## 13. 结论

当前系统**已自发贴合 DAM + 混合检索 + 离线优先三大最佳实践主线**，在「索引可重建」「受控分类法」「引用完整性五层保障」「语义补召回不喧宾夺主」四点上有明确工程洞见，是扎实的 v1.0 单机产品。

**最大、最该先补的差距是安全（无鉴权 + 路径校验，P0）**——它决定了这套系统能不能离开「可信局域网」；其次是**把已测出的检索质量用评估门禁锁死（P0-3）**，避免后续优化把 0.71 改回去。

**最具杠杆的下一步（P1）** 是「**自动打标 + 多语语义**」：前者直接喂肥 Agent 最需要的元数据，后者根除中文检索对同义词表的依赖——两者叠加后，素材中心将从「可搜的索引」升级为「Agent 能读懂的素材大脑」。

> 本文档为评估与规划，不含代码改动；落地时按 P0→P1→P2 推进，每步以 `eval_search.py` 为回归闸门。

## 15. 业界最新实践补强（2026 检索与对齐）

> 本节基于 2026 年公开资料（WorkOS《Everything your team needs to know about MCP in 2026》、
> MCP 官方概念、掘金《RAG 架构设计全景：从 Chunk 策略到生产级 Agentic RAG》、Cloudinary/Daminion
> 等 DAM 厂商实践）的检索结果，提炼与本项目直接相关、且当前文档尚未充分覆盖的条目，并标注已对齐项。

### 15.1 MCP 2026 协议新范式（直接对应本文 E 维度）
- **Tools（写侧）与 Resources（读侧）分离**：只读、订阅式数据应做成 Resource（Agent 像读文件一样拉取），写操作才用 Tool。本项目把「最近登记 / 某 job 全套」做成 Resource，正是这条。
- **Prompts 模板**：把「如何与领域交互」固化为可复用 prompt 模板随 server 分发；本项目可在未来把「素材检索工作流示例」固化成 prompt。
- **Sampling / 服务端 agent loop**：server 可在执行中请求模型补全（校验中间状态、生成内容），敏感场景保留人在环。
- **Elicitation（人机澄清）**：安全敏感步骤用 URL 模式跳转、结构化澄清用表单模式——正好对应本项目「写操作需 `confirm=true` + 人工复核」的护栏思路。
- **动态能力协商（extensions）**：`initialize` 应按运行环境声明能力，而非回固定值。本项目已实现：按 embedding/reranker/token 可用性动态声明。
- **远程鉴权**：跨机时用 OAuth 2.1 + PKCE + CIMD + Resource Indicators（防 token 跨服复用）+ 会话级限时 token；本机 stdio 继承宿主权限即可（本项目当前即 stdio 本机模型）。
- **降 token 膨胀**：Cloudflare「Code Mode」动态发现工具（实测省 98%+ token）、窄作用域 token。本项目 `_brief()` 字段裁剪已贯彻，下一步可对万级结果做 cursor 分页。

### 15.2 生产级 RAG（对应本文 C 维度）
- **父子分块（Parent-Child）**：子块 ~400–512 token 精检、父块 ~2000 token 喂生成；中文按 `。， ` 递归切分，`chunk_overlap` 10–20%。本项目长笔记整段当 doc_text，可改进为按段落分块 + chunk 级元数据。
- **二阶段重排（cross-encoder reranker）**：bi-encoder 召回 Top-50~100 → `bge-reranker-v2-m3` 精排 Top-5~10，NDCG@10 0.65→0.78（+20%）。**本项目已实现可选的 stage-2 重排（见下）**。
- **量化评估驱动 A/B**：用 RAGAS 的 Context Precision/Recall、Faithfulness 等做基线，弱指标定向修、再复测。本项目 `eval_search.py` 的 P@5/R@20 门禁同此思路。
- **语义缓存**：Redis 语义缓存（相似度阈值 0.85）降本 30–50%、延迟 2–5s→<50ms。本项目可加一层查询→结果的内存/磁盘缓存（同义查询重复率不低）。

### 15.3 DAM / AI 标注（对应 A / H 维度）
- **粒度权限 + 审计**：DAM 厂商（Daminion/DBGallery）强调细粒度权限与多租户隔离；本项目单机个人级，权限=token 开关即可，但「谁在何时改了标签」仍建议加 `history` 表。
- **AI 自动打标 / 内容理解**：厂商把 AI tagging 当标配；本项目 `auto_tag`（写 `ai_tags` 隔离列，不污染词法）已走对路。
- **与创作工具集成**：DAM 价值在「能被下游工具消费」。本项目 `bridge_subtitle` + MCP 正是把素材喂给 Agent 的生产集成。

## 16. 素材中心系统存储与压缩方案（容量规划 + 压缩优化参考）

> 来源：2026-09-28 一份 AI 生成草案（标注「AI 生成可能有误，注意核实」）。本节**不与 §0 的当前实现混淆**：
> 本项目现在是一个**单机个人级**索引器（零依赖、全离线、344 条 / ~3.3GB，SQLite 索引 + 磁盘原文件，不做转码），属于下表「MVP 起步」档位之下的更轻量形态。
> 本节内容属于**面向规模化部署的前瞻参考**（容量基线、三文件分离、编码/去冗余/分层、服务器规划、踩坑），数字为行业经验量级、需按实际校验，落地前请核实。

### 16.1 核心问题：是不是需要大量服务器 / 存储？

**结论**：原始素材库天然吃存储，但 **90% 的磁盘压力可靠架构设计降下来**，不需要盲目堆磁盘服务器。最大误区是「把原始高清母版全部做在线热存储」——95% 素材平时只有 Agent 做检索 / 打标签 / 摘要，几乎不会下载原始母版。

不同规模资源基线（短视频 / 影视混剪素材库）：

| 规模 | 素材总量 | 存储压力 | 服务器最小配置 |
|---|---|---|---|
| MVP 起步（1 万条短视频素材） | 单条 1–5min，原始 1080P | 原始总容量 20–60TB | 无需独立存储集群：对象存储（云 COS/TOS/MinIO）；2 台 8–16 核转码机（带 NVENC 显卡）；1 台业务后端；1 台向量库机器（16–32G 内存） |
| 中小商用（10 万条） | 大量影视片段、混剪素材 | 原始 300–800TB | 对象存储为主，本地只放热代理文件；4–8 台转码节点；向量库独立机器；数据库独立 |
| 生产级百万级素材 | 影视剧切片、综艺、短视频 | PB 级别 | 必须分布式对象存储，冷热分层，转码集群弹性扩缩容 |

### 16.2 核心架构：「三文件分离」（降本基石）

Agent 日常只做检索 / 画面理解 / 打标签 / 摘要 / 镜头识别 / 片段检索，**根本不需要读 4K 原始母版**，只需代理小样（Proxy）。三层物料分开独立存储：

- **① 原始母版（Master）**：最高画质，只用于最终导出下载；平时几乎不访问 → 放低频 / 归档存储，不要放高性能 SSD / 标准存储。
- **② 代理小样 Proxy（AI-Agent 日常分析用，重中之重）**：720P–540P，H.265，低码率 1–3Mbps，音频 AAC-128k。Agent 全部 AI 分析（镜头分割、画面描述、OCR、语音转写、向量特征）都基于这份小样，绝不碰母版 → 热 / 标准存储，访问频率最高。
- **③ AI 特征资产**（向量库、关键帧缩略图、字幕 SRT、镜头元数据、音频 embedding）：
  - 向量库（Milvus/Qdrant）只存 embedding，体积极小：100 万素材向量仅几十 GB；
  - 关键帧只保存镜头切换帧（不要每秒一帧、按场景变化抽帧），体积可降 80–90%。

**业务数据流**：上传源文件 → 异步流水线：转码生成 Proxy + 提取关键帧 + 语音转写 + 镜头分割 + 多模态向量入库；原始母版直接沉降至低频存储；日常 Agent 全部读 Proxy；用户要下载成片时，才从归档把母版临时取回。

### 16.3 视频压缩四个层级（业务架构 → 编码 → 内容智能去冗余）

**层级 1：编码层压缩（最直接，可省 40–55%）**
- 优先编码排序：AV1 > H.265(HEVC) >> H.264。H.265 同等画质比 H.264 省 45–50%，NVENC 硬件加速适合 Proxy；AV1(SVT-AV1) 再省 20–25%，但编码慢，适合历史素材批量归档（后台闲时），不要做实时流水线。
- Proxy 用 H.265；归档母版可用 AV1 长期归档；**不要用软件 x265 做实时流水线**（速度跟不上），一定要 NVENC 硬件编码池。
- 不要无脑 4K：Proxy 最高 720P 足够 AI 识别（多模态模型对超 720P 收益≈0），4K 只保留原始母版。

```bash
# H.265 硬件代理小样模板（720P，素材中心 Proxy 标准模板）
ffmpeg -i source.mp4 -vf scale=1280:720 -c:v hevc_nvenc -preset p5 -cq 27 -c:a aac -b:a 128k proxy.mp4
```

**层级 2：内容智能去冗余（影视素材特别适用，常被忽略）**
- 场景检测，只保留镜头切换关键帧：用 scenecut 检测镜头变化，静止长镜头只保留首尾帧，中间帧丢弃 → 关键帧存储量降 70–90%；不要固定「1 秒抽 1 帧」。
- 黑屏 / 纯色片头片尾自动检测标记，不纳入检索库、不存多余帧。
- 素材指纹去重：上传流水线计算视频感知哈希（pHash + 多模态 embedding），near-duplicate 近重复素材直接拒绝入库或只存一份母版、多条元数据引用。**关键点：元数据可以多份，实体视频文件只存一份，引用计数管理**——这是素材库后期最大的空间黑洞。

**层级 3：存储分层策略（成本优化最大杠杆，省 60–85% 账单）**
- 云上（COS/TOS/OBS/七牛 KODO）：Proxy 热数据走标准存储；原始母版生命周期自动流转——上传 30 天→低频（约标准 50%）；90 天未访问→归档闪回（标准 1/4–1/5，取回 5–15 分钟）；180 天几乎不用→冷归档（成本 1/20，取回几小时）。85% 素材 90 天不会下载母版。
- 私有化本地：热层 SSD/NVMe 只放 Proxy + 关键帧 + 向量库；温层大容量 SATA-HDD 放近期母版；冷层蓝光磁带 / 归档 HDD 离线池放历史影视剧母版。**私有化千万不要把全部母版跑在 SSD 上**。
- 开源私有化选型：MinIO（S3 兼容，智能生命周期，本地冷热分层；纠删码 EC 模式不用多副本，磁盘利用率 75–80%，普通三副本仅 33%，有效容量翻倍多）。

**层级 4：Agent 侧「逻辑压缩」，降低 AI 计算与 IO 压力**
- 不每次读取完整视频：建镜头索引表（每素材镜头时间轴 `[{start,end,scene_desc,frame_key}]`），Agent 按元数据定位时间戳，只切片读取该片段 → IO 降 90%（FFmpeg `-ss` 按时间截取）。
- 语音不每次重跑 ASR：一次 Whisper 转写生成 SRT 存入库，后续 Agent 直接读文本字幕，不反复解码音频。
- 多模态向量只计算一次入库，不每次查询都重跑画面大模型。

### 16.4 服务器资源规划（MVP / 商用两版）

**MVP 版本（1–10 万素材，最经济）**
- 存储层：直接云对象存储，不开自建分布式；MinIO 只做测试；生产优先云 COS/TOS 开智能分层、按量付费，不一上来买几十 TB 本地盘（90% 前期闲置）。
- 转码 / 预处理节点（最重要）：1 台 RTX4060-8G（NVENC 硬件转码）+ 8–16 核 / 32G；FFmpeg 流水线异步转码、生成 Proxy、抽关键帧。**转码是异步后台任务，不要和业务 API 混一台机**（CPU/GPU 占用极高）。
- 业务后端 API：8 核 16G（NestJS/FastAPI），负责元数据管理、Agent 调度、权限。
- 向量检索机：16–32G 内存，Milvus-standalone，10 万素材内单机够用。

**商用生产版本（10–100 万素材）**
- 转码集群：多台 NVENC 机器 + RabbitMQ/Kafka 任务队列，上传任务丢队列、多机弹性消费；闲时扩容批量转码，高峰只处理新上传。
- 存储：对象存储集群 + 冷热分层自动流转 + 纠删码 EC（放弃简单三副本）。
- 向量库 Milvus 集群：分片分布式，多模态向量分开索引（画面 / 音频 / OCR 文本）。
- 业务、数据库、Agent-Worker 物理隔离：Agent-worker 单独一组机器跑多模态分析 / 镜头描述 / 标签生成，不占 web 接口资源。

### 16.5 常见踩坑清单（行业落地教训）

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | 直接拿原始高清视频喂 Agent：4K 解码 IO 巨大、GPU 内存暴涨、速度慢几倍 | 必须用 Proxy 代理小样（芒果 / 爱奇艺媒资库均此架构） |
| 2 | H.264 全部入库不转码 | 后期存储 3–5 倍膨胀 |
| 3 | 实体文件多副本，同一段反复存 | 只用引用计数：一份实体、多条元数据 |
| 4 | 全部放标准热存储，历史 9 个月不用的片段仍按高价计费 | 冷热分层生命周期流转 |
| 5 | 关键帧每秒抽 1 帧：2 小时电影 21600 张图，几十万素材下图片几十 TB | 按镜头场景抽帧，而非按时间 |
| 6 | 同步转码：上传完等转码才返回，接口超时 | 异步消息队列，上传立即返回，后台排队 |

### 16.6 可直接复制的流水线顺序（上传完整工作流）

### 18.1 核心论点（原文精华）

传统 DAM/媒资系统**只管理文件，不理解内容**；素材 Agent 是具备自主规划、执行、调用工具的智能体，把素材从"存储文件"变成**可被 AI 直接调用的业务资产**。最大价值一句话：**不需要人工打标签、整理、检索、切片；上传之后 Agent 自主完成全链路解析，并可直接给下游 AIGC/剪辑 Agent 输出可用片段，实现「素材入库‑理解‑检索‑二次创作」闭环**。

**与普通 AI 插件的本质区分**：普通插件是被动调用（人点按钮才识别）；素材 Agent 是**事件驱动、自主调度工具链**，且自身可作为工具被其他 Agent 调用。

### 18.2 五大能力 × 本项目现状对照

### 20.2 本轮已落地（2026-09-30）

**缺口 1 — 后台异步执行（纯工程，零模型依赖）**
- `mcp_server.t_agent_run` 不再同步调用 `agent_run`：预生成 `task_id` → 后台 `threading.Thread(daemon=True)` 跑
  `agent.agent_run(task_id=...)` → 立即返回 `{"status":"running","task_id":...}`；调用方用 `agent_status` 轮询。
- `agent.agent_run` 主循环**每步 `_save(state, ws)`** 落盘，使 `agent_status` 可实时反映进度（此前仅收尾落盘）。
- 写护栏不变：`confirm=true` 才向 agent 传 `allow_write`；无 chat 模型时状态落 `skipped`，轮询可见。
- 验证：`agent_run` 保持同步返回最终 dict（既有 9 例测试全绿），后台化只发生在 MCP 层，不影响单测。

**缺口 2 — finish 的确定性核验 + 诚实弃权（确定性，对 7B 友好）**
- `agent.py` 新增 `_collect_ids(obs)` + `ctx["seen_ids"]`：全程累计 search/get_material/retrieve 真实返回的素材 id。
- `finish` 时若带 `ids`，逐一比对 `seen_ids`：**未出现的一律剔除并标注** `[核验] 已剔除 N 个…`，存入 `result_ids`/`dropped_ids`（返回与 `agent_status` 均暴露）。
- `_LOOP_SYS` 新增第 8 条「诚实弃权」规则：连续 0 命中须如实说明、严禁编造 id/结论；宁可少答不可胡答。
- 验证：新增 `test_finish_drops_unseen_ids`（声明 `ids:["m1","fake999"]` → `result_ids=["m1"]`、`dropped_ids=["fake999"]`）；套件现 **10/10 绿**。

### 20.3 本轮续做落地（2026-09-30 同日，P1 两项）

**缺口 3 — 跨任务 playbook 长期记忆（确定性，零模型）**
- `agent.py` 新增 `index/agent_workspace/agent_memory.json`（落在 `WORKSPACE` 下，派生数据，测试随重定向隔离）：任务 `done` 且有 `result_ids` 时，

### 20.4 本轮续做落地（2026-09-30 同日，P2 缺口 4）

**缺口 4 — 确定性 Critic + 结构化引用溯源**
- `agent.py` finish 阶段新增两块（均确定性、零模型）：
  1. **结构化引用 `citations`**：`finish` 可附 `citations:[{claim,id}]`，逐条校验 `id` 是否在本任务检索白名单 `seen_ids` 内，越界即剔除并标注 `[核验]`；存入 `state.citations`（含 `valid` 标志）。
  2. **确定性 Critic**：用正则 `[0-9a-f]{12}` 扫描总结正文里的素材 id（素材 id 即 `sha[:12]` 十二位十六进制），凡不在本次检索白名单内一律标记 `[Critic]` 并剔除相关引用——专治 7B 在自由文本里编造 id 的幻觉。

### 20.5 本轮续做落地（2026-09-30 同日，P2 缺口 6）

**缺口 6 — 动态上下文压缩（防 context-rot）**
- 原 `agent.py` 主循环只发 `context[-6:]` 给模型，更早的步骤被**直接丢弃**，本地 7B 长任务会"忘了开头"。
- 新增**确定性滚动摘要**：每步后若 `len(context) > _CONTEXT_TAIL(6)`，被逐出窗口的早期 `stepN[action] <obs>` 行压入 `digest`（`_DIGEST_MAX=30` 行封顶防无限增长），并在构造 prompt 时以「(前情压缩摘要,早期步骤已归档,无需重做)」前缀回灌给模型。全程零 LLM、零网络。
- `state["context_digest"]` 每步落盘（供 `agent_status` 实时可见），`agent_run`/`agent_status` 返回均暴露该字段。
- 价值：对应 Anthropic "context rot / 上下文卸载" 实践——长任务早期决策不再丢失；7B 无需重做已归档步骤。
- 验证：新增 `test_context_compression_rolling_digest`（8 步巡检任务 → 摘要含 `step1[`/`step2[`、不含 `step8[`、≥2 行）；套件 **15/15 绿**；MCP 层 **5/5 绿**。短任务（≤6 步）`digest` 为空，行为完全不变。
